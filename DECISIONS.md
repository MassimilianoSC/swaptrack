| c3 | Vite dev server on port 3000 forwards the emulator endpoints (same origin). Configured only in `vite.config.ts` (proxy) and `src/lib/data/firebase.ts` (connection), development only. |
| c4 | Template `frontend/` and `backend/` deleted; the root Vite app runs. |

| D1 | Firestore emulator on port 8180: 8080 is taken in this environment. |
| D2 | `scripts/emulators.sh` sets `GCE_METADATA_HOST=127.0.0.1:1`: without a metadata server the CLI hangs before starting. |
| D3 | Location and model ids are deterministic (`loc_<encoded code>`, `mdl_<encoded normalized materialCode>`): uniqueness of `code`/`materialCode` by construction; import upsert by code. |
| D4 | Import: changing the ASP of an existing **site** through import or `saveLocation` is refused (`asp_change_use_reassign`): it must go through `reassignSite`, which moves the pieces with `force_state` events. Location type and code are immutable. |
| D5 | Import of sites: the "type" column accepts `site`, `asp_warehouse`, `client_warehouse`; the ASP column accepts the ASP name (case-insensitive) or its id. The list of records missing from the file is computed in the browser of the client_admin (who can read all locations/models); deactivation through the same import op (`mode: "deactivate"`). |
| D6 | Re-enabling a deactivated user: `deactivateUser {uid, reactivate: true}` (no separate op in §19.2). Re-enabling an ASP does not reactivate its users. |
| D7 | `signOutEverywhere` can be called on oneself (Profile) or by a manager on a person they manage. Revokes refresh tokens without disabling. |
| D8 | `deleteUser`: user document keeps `role`, `orgId`, `deleted: true`; e-mail and names set to null; Auth account deleted. Last-admin check applies. |
| D9 | Invitation/reset links: the server generates the Firebase link and rewrites it to `APP_URL/auth/action?mode=resetPassword&oobCode=…&purpose=invite|reset&lang=…`, so the custom handler on the app's own domain works without console configuration. |
| D10 | Changing the privacy notice text automatically bumps the version (everyone accepts again); the admin can also bump without changing text. |
| D11 | Logo uploaded through `saveSettings` (base64, max 500 KB, PNG/JPEG/SVG/WebP) and written by the server to `branding/logo.<ext>`: clients never write to Storage paths other than photos/documents. |
| D12 | Shell: technicians always field shell; ASP warehouse/admin field shell below 768 px; client roles always desk shell (light) with a drawer on phones. |
| D13 | Seed: invented names on `swaptrack-demo.test`, password `SwapDemo2026`. The platform suggested using the owner's real e-mail for the admin account; not done because §0.8 forbids real e-mail addresses. |
| D14 | Inactivity sign-out never signs out while scans or photos are pending (same rule as manual sign-out). |
| D16 | Events are processed by one Firestore trigger `onEventCreated` (retry on); the item state is always recomputed by replaying all non-voided events of the item ordered by `at`, then `createdAt`, then `id` (§8.2). |
| D17 | Server-written events (`source: "server"`, e.g. `force_state`, `confirmReturn`) skip the client codeId-mismatch check; the server recomputes the codeId from `codeRaw`. |
| D18 | Sorting rules: an active rule with the same keys (site, model, equipment type) as another active rule is refused (`rule_duplicate`); a rule needs at least one key. Precedence: site+model > site+type > model > type > site. |
| D19 | Seed adds 3 sorting categories (reuse, refurbish, scrap) and one rule (type "Radio unit" → refurbish). |
| D20 | Step 3 is finished in 4 sub-steps (3A server corrections/tests, 3B item pages + "to complete" + model pick, 3C photos, 3D shipment pages); details in `NOT_DONE.md`. Proposed, waiting for the owner's approval. |
| D21 | A copy of the supervisor config lives in `scripts/supervisor/swaptrack.conf` (the live one in `/etc/supervisor/conf.d/` is outside `/app` and may not survive a fork or pod restart): `sudo cp scripts/supervisor/swaptrack.conf /etc/supervisor/conf.d/ && sudo supervisorctl reread && sudo supervisorctl update`. |
| D15 | Scheduled jobs use the European time zone `Europe/Rome`. Grace expiry runs daily: an account is disabled between 7 and 8 days after deactivation. |
| D22 | **Resolution of `code_of_another_asp` uses a server `force_state` event one instant before the triggering arrival**, instead of a server `transfer_out`. SPEC §9.2 describes the resolution as a server `transfer_out`, but `transfer_out` from `installed` is forbidden by the state machine and would require a synthetic shipment to carry the destination ASP. `force_state({aspId: destinationAsp})` is written with `scannedAt = arrival.scannedAt - 1ms`: the replay then moves the piece to the destination ASP, so the arrival applies normally. The anomaly is marked `resolution: "forced"` and recorded in `adminLog`. Only `client_admin` may do it (§3.3). |
| D23 | **Merge re-point and replay**: `mergeItems` sets `mergedInto` on the merged item inside a transaction, re-points `codes` and `events` with `itemId == from` to `into` in batches of 450, then writes a server `force_state` (no state change) on the canonical item so the trigger replays with the newly-pointed events. The trigger always follows `mergedInto` (up to 5 hops, then `merge_chain_suspicious`). |
| D24 | **`correctEventLocation` keeps the original values in `event.correction`** `{previousLocationId, correctedBy, correctedAt, reason}` and writes a server `force_state` so the item is replayed. The event's `aspId` is unchanged (it stays the ASP of the recorder); `locationAspId` is resolved from the location at replay. |
| D25 | **Replay on an unknown code with a wrongly-located event** (`classify` or `arrive_at_warehouse` at a site, `install_at_site` at a site of another ASP) returns no piece: the event is kept, the trigger raises `forbidden_transition` and marks the event processed with `outcome: forbidden_transition`, no `items` or `codes` doc is written. §9.2 "unknown code -> natural state" does not override §9.2 "forbidden transitions". |
| D26 | **Transfer "to send" / "incoming" split and the 7-day `transfer_difference` alert are grouped on the single `/shipments` list** (filterable by role), to keep step 3 within scope. The dedicated split and the scheduled alert come in step 4 (NOT_DONE.md). |
| D27 | **Scan-screen shipment-draft burst mode** is reached by query parameters `?mode=return_ship|transfer_out&shipmentId=…`, so no second scanner page is built. `arrive_at_warehouse&shipmentId=…` is used by the receiving ASP for a transfer arrival. |
| D28 | **Model pick for unknown pieces** is shown on the scan screen for `remove_at_site` and `arrive_at_warehouse` (the two position events that can create a piece naturally). The user can pick a model or skip; a skipped piece gets `needsModel: true` and appears in `/items/to-complete`. |
| D29 | **Document files are stored under `documents/{aspId\|client}/{kind}/{documentId}/{n}.{ext}`** (DECISIONS b5 revision in extra step) with the file index starting at 1 (not 0); `kind` is in the path so `storage.rules` gate reads by kind (asp_technician can read BOM files of their own ASP, client_warehouse can read `ddt_return` files, as in §3.3). The server accepts PDF, JPEG, PNG, WebP, Excel (.xlsx), CSV; max 5 MB per file (R: §7.3). The owner's product list limits files per save to 10. |
| D30 | **Reports and exports are real PDF (pdfmake) and Excel (exceljs) files** written in the organization language (R14): `reports/{scope}/{month}.pdf`, `reports/{scope}/{month}.xlsx`, `exports/{scope}/{ts}.xlsx` (`functions/src/shared/reportBuilders.ts`). pdfmake uses PDFKit built-in Helvetica so no external TTF files are needed in the Cloud Function runtime. Strings are in `functions/src/shared/reportStrings.ts` (Italian + English); organization language is read via `functions/src/core/orgLang.ts` from `organizations/{id}.language`, defaults to Italian when empty. |
| D31 | **Deterministic alert ids** (SPEC §11.4) live in `functions/src/shared/alertIds.ts`: `stale-{locationId}-{flow}`, `bom-{documentId}`, `ddt-{documentId}`, `transfer-{shipmentId}`, `return-{shipmentId}`. One alert per object, not per piece; `merge` with `count` + `detail` updates. |
| D32 | **BOM check runs in two places**: inside the trigger on `site_done` for that site, and daily between 24 and 48 hours after the last scan at a site when there was no `site_done` (SPEC §11.3). The BOM check compares `remove_at_site` and `install_at_site` events after the BOM's `createdAt` against the BOM lines by direction. |
| D33 | **The DDT-arrival link rule** (SPEC §11.3): an arrival counts for a `ddt_in` document only when `event.payload.ddtId == documentId` **or** the arrived code is a serial line of the document. The scan screen passes `?ddtId=…` when the warehouse user opens a DDT from the document page and scans from there. Live counters on the scan screen are computed on the device from the user's own events joined with the ASP's items and codes in the cache (R11). |
| D34 | **Items carry `currentRegion`** copied by the trigger from the location at every state write, so the `statusByRegion` aggregate (SPEC §13.1) does not need a cross-service read when a dashboard reads from a shard. |
| D35 | **Aggregates: nightly recount rewrites shard 0 and clears shards 1-9**, so a dashboard reading 10 shards always sums to the recounted total; between recounts the trigger spreads increments across the 10 shards. |
| D36 | **`revealEventAuthor` for server events returns `null`** (no name): a server event has no human author to reveal. |
| D37 | **`fieldPolicy.pieceAtSiteNotInBom`** (SPEC §14) is read by the technician scan screen; "accept and alert" raises a `bom_difference` through the trigger's BOM check at `site_done` or by the daily job; "accept silently" skips the alert. The scan is always accepted (SPEC: `required` in `itemFields` means "appears in to-complete", never blocks a scan). |
| D38 | **BOM tick list on the technician scan screen** (§12.1 point 4) is computed on the device from the user's own events (today, including those with pending writes) joined with the ASP's BOM documents in the local Firestore cache. Direction comes from the mode (`remove_at_site` → remove, `install_at_site` → install); every reading ticks a line, unexpected codes are listed below. `src/lib/data/events.ts` → `primeFieldCache` loads BOM documents of the ASP into the cache at sign-in; `cachedBomForSite` reads the newest open or checked BOM for the site from the cache. `firestore.rules` allows `asp_technician` to read BOM documents of their own ASP. |
| D39 | **The demo installation runs on the reused Firebase project `kronos-caffe-sito`, renamed "SwapTrack Demo"** (owner's decision, 29/10/2026). App served from the dedicated Hosting site `swaptrack-demo` (target `app`); configuration in `.env.demo` and `functions/.env.kronos-caffe-sito`. See README, section "Progetto Firebase della demo". The project also has a Google Analytics measurement ID from its old use: SwapTrack never loads Analytics (R12). |
